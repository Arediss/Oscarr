## Data and upgrade behavior

The release now includes additive migrations for routing tags, request season numbering and
durable post-migration jobs. The metadata upgrade queues one full sync for existing enabled
Sonarr/Radarr libraries; completed work is not replayed on restart. See
[service metadata](../service-metadata.md) and [post-migration jobs](../post-migration-jobs.md).

`20261030230000_patchnote_0100` installs the final bilingual release notes through SQL. It
upserts only version 0.10.0, preserving its existing ID and all other releases. The development
startup seed is removed so it cannot overwrite the SQL content. This note-only migration
does not enqueue another sync or reset library data.

`20261030233000_patchnote_0100_date` aligns the 0.10.0 date with the historical ISO-text
storage format. SQLite sorts text ahead of integers in descending order, so the draft's
millisecond timestamp placed 0.10.0 below older releases and outside the 15-note API window.
The corrective migration preserves all earlier dates and migration checksums.

Before production restart, retain a verified SQLite backup and the previous image for rollback.
This content migration changes no schema and needs no database rollback to run the previous
image. The previous development image would reinsert its draft note at startup; redeploying
the new image after that requires reapplying this note's upsert and date correction, since Prisma has already
recorded the migration. Do not reset the database or delete migration history for this.

Grouping changes presentation and pagination; request IDs, users, season scopes, statuses and approval actions remain separate. Existing pending collection requests are not retroactively approved. The ordinary row-based request API remains available when `groupBy=mediaUser` is omitted.

## Expired browser sessions (2026-11-01)

- A protected API response with `401 / UNAUTHORIZED` now clears the current user and
  permissions, so the existing route guard returns to login without a page reload.
  `403 / ACCOUNT_DISABLED` also invalidates the session. Permission denials, invalid login
  or backup passwords, installation-secret failures and transient server/network errors
  retain their existing handling.
- In-flight requests carry an in-memory session version. Concurrent failures expire once,
  old failures cannot invalidate a new login, and a delayed `/auth/me` response cannot
  restore a signed-out user. Manual logout waits for the cookie-clearing response before
  exposing the login form. Cookies, session lifetime and backend authorization are unchanged.
- Twelve Axios regression tests reproduced four failures before the fix. All 363 backend
  and 191 frontend tests pass; the production build passes with its existing chunk warning.
  Browser verification uses the real auth provider, API interceptors, route guard and login
  form with isolated transport fixtures: expiry redirects, polling stops, delayed user data
  stays ignored, wrong credentials display their error, and login works without reloading.
- Independent review checked the lifecycle and logout race. No SQL migration or data reset.
- Dependency audit on 2026-11-01 reports 15 pre-existing findings (1 high, 12 moderate,
  2 low); the lockfile is unchanged. The high finding,
  [GHSA-mrwp-f3q8-3g9p](https://github.com/advisories/GHSA-mrwp-f3q8-3g9p), requires a
  cross-realm `sensitiveHeaders` array: no such usage or VM context exists in the application,
  and the installed Axios adapter normalizes its array. No reachable path was identified
  for this specific advisory. External plugin code is outside this reachability assessment.
  The pre-publication update below resolves this finding. Remaining findings concern
  glob/minimatch and build-time deepmerge.
